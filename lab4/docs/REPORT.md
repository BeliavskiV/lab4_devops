## 3. Задание 1. Подготовка окружения для локального кластера

### 3.1. Используемые инструменты
* **Docker Desktop:** контейнерный движок; kind использует его как провайдер нод кластера.
* **kind (Kubernetes in Docker):** утилита для запуска локального кластера Kubernetes в Docker-контейнерах.
* **kubectl:** консольная утилита для управления кластером.
* **Kubernetes (kindest/node:v1.37.0):** образ ноды кластера.

### 3.2. Конфигурация кластера (`task1/kind-config.yaml`)
```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: lab4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30000
        hostPort: 30000
        protocol: TCP
  - role: worker
  - role: worker
```

### 3.3. Создание и проверка кластера
```bash
kind create cluster --name lab4 --config task1/kind-config.yaml
kubectl cluster-info
kubectl get nodes -o wide
```
Все три ноды (`lab4-control-plane`, `lab4-worker`, `lab4-worker2`) перешли в состояние `Ready`, контекст установлен на `kind-lab4`.

## 4. Задание 2. Знакомство с ресурсами Kubernetes

### 4.1. Системные поды и их назначение
Команда `kubectl get pods -A` выводит следующие системные компоненты в пространстве имён `kube-system`:
* **`etcd`** — распределённое key-value хранилище состояния кластера.
* **`kube-apiserver`** — REST API, единая точка входа в кластер.
* **`kube-controller-manager`** — контроллеры, приводящие состояние к желаемому.
* **`kube-scheduler`** — планировщик подов по нодам.
* **`kube-proxy`** — сетевая маршрутизация и правила iptables.
* **`CoreDNS`** — внутренний DNS-сервер кластера.
* **`kindnet`** — CNI-плагин для межподовой сетевой связности.

### 4.2. Работа с томами
1. **`emptyDir`:** создан под (`task2/pod-volume.yaml`) с двумя контейнерами (`writer` и `reader`), монтирующими общий временный каталог `/data`. Контейнер `reader` успешно читает файлы, записанные `writer`.
2. **PersistentVolume / PersistentVolumeClaim:** настроен PVC (`task2/pvc.yaml`) и под (`task2/pvc-pod.yaml`), использующий динамический провизионер `local-path-storage`. Проверено, что при удалении и пересоздании пода данные на диске сохраняются.

### 4.3. ReplicaSet
Создан `ReplicaSet` (`task2/replicaset.yaml`) с 3 репликами `nginx`. Проверено автоматическое масштабирование (`kubectl scale --replicas=5`) и механизм самовосстановления (при удалении пода контроллер мгновенно создаёт новый).

## 6. Ответы на контрольные вопросы

1. **Что такое Kubernetes и зачем он нужен в работе с контейнерами?**  
   Это платформа оркестрации контейнеров с открытым исходным кодом, автоматизирующая развертывание, масштабирование и управление распределенными приложениями. Нужна для устранения ручного управления множеством контейнеров на разных серверах.

2. **В чём отличие «запустить контейнеры вручную через Docker» от «управлять ими в Kubernetes»?**  
   Docker управляет изолированными контейнерами на одной машине без встроенных механизмов самовосстановления, декларативного масштабирования и балансировки. Kubernetes управляет кластером нод, автоматически поддерживая заданное пользователем состояние (Desired State).

3. **Примеры задач, где оркестрация экономит время:**  
   Автоматический перезапуск упавших инстансов, бесшовная выкатка обновлений (rolling update) без простоя сервиса, динамическое горизонтальное масштабирование под нагрузкой.

4. **Основные компоненты кластера Kubernetes:**  
   *Control-plane:* `kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`.  
   *Worker nodes:* `kubelet`, `kube-proxy`, container runtime (containerd), CNI-плагин.

5. **Обязательные поля YAML-манифеста пода:**  
   `apiVersion`, `kind`, `metadata` (включая `name`), `spec`.

6. **Что произойдёт, если пропустить одно из обязательных полей?**  
   API-сервер Kubernetes отклонит манифест на этапе валидации и вернет ошибку создания объекта.

7. **Что такое сервисы в Kubernetes и зачем они нужны? Разница между ClusterIP и Headless:**  
   Service — абстракция, объединяющая поды под единым стабильным IP-адресом и DNS-именем.  
   *ClusterIP* выделяет единый виртуальный IP для балансировки трафика внутри кластера.  
   *Headless* (`clusterIP: None`) не выделяет виртуального IP, а возвращает через DNS IP-адреса конкретных подов напрямую.

8. **Чем отличаются сервисы NodePort и LoadBalancer?**  
   *NodePort* открывает одинаковый порт на каждой ноде кластера для внешнего доступа.  
   *LoadBalancer* создает внешний облачный балансировщик нагрузки перед NodePort-сервисом.

9. **Какие порты задействованы и какие ограничения есть у NodePort?**  
   Диапазон портов по умолчанию: `30000–32767`. Ограничения: высокие номера портов, отсутствие встроенного TLS и сложной маршрутизации доменов.

10. **Пример, когда NodePort достаточно, а когда нужен LoadBalancer:**  
    *NodePort* достаточен для локальной разработки (как в kind) и тестовых стендов. *LoadBalancer* необходим в продакшене в облачной среде для получения выделенного публичного IP.

11. **Что такое Ingress и какую проблему он решает?**  
    Ingress — это объект маршрутизации уровня L7. Он решает проблему публикации множества микросервисов через единый внешний порт (80/443) с поддержкой виртуальных хостов и TLS-терминации.

12. **Сравнение Deployment, StatefulSet и DaemonSet:**  
    * *Deployment:* для stateless-приложений, поды взаимозаменяемы.
    * *StatefulSet:* для stateful-систем (СУБД), поды имеют постоянную идентичность и упорядочены.
    * *DaemonSet:* запускает ровно по одному экземпляру пода на каждой подходящей ноде (агенты сбора логов, мониторинг).

13. **Разница между Job и CronJob:**  
    *Job* запускает задачу до её успешного одноразового завершения. *CronJob* создает Job по заданному расписанию (cron-формат).

14. **Для чего нужны ConfigMap и Secret? Два способа передачи в под:**  
    Для отделения конфигураций и конфиденциальных данных от кода приложения. Способы: 1) Переменные окружения (`envFrom`); 2) Монтирование в виде файлов через тома (`volumeMounts`).

15. **YAML-фрагменты для ConfigMap и Secret; почему пароли нельзя хранить в ConfigMap:**  
    ConfigMap не шифруется и доступен в открытом виде любому пользователю с доступом к чтению объекта в namespace, в то время как Secret специально спроектирован для конфиденциальных данных.

16. **Основные команды kubectl по группам задач:**  
    * Состояние: `kubectl get`, `kubectl describe`, `kubectl logs`.
    * Создание/обновление: `kubectl apply -f`, `kubectl set image`, `kubectl scale`.
    * Удаление: `kubectl delete`, `kubectl rollout undo`.
    * Отладка: `kubectl exec -it`, `kubectl port-forward`.

17. **Что такое пространства имён (namespaces) и зачем они нужны?**  
    Логические изолированные виртуальные кластеры внутри одного физического. Нужны для изоляции команд, сред (dev/stage/prod) и разграничения прав доступа.

18. **Как создать новое пространство имён и выполнять команды в нём:**  
    `kubectl create namespace <name>`, а для работы без флага `-n`: `kubectl config set-context --current --namespace=<name>`.

19. **Зачем нужны пробы (probes):**  
    * `livenessProbe` проверяет, живой ли контейнер (перезапускает при зависании).
    * `readinessProbe` проверяет готовность принимать трафик (исключает из балансировки).
    * `startupProbe` защищает медленно стартующие приложения.

20. **Что такое Persistent Volume (PV) и Persistent Volume Claim (PVC):**  
    *PV* — физический ресурс хранения в кластере. *PVC* — запрос пользователя на выделение этого хранилища нужного размера и режима доступа.

21. **Как Kubernetes реагирует на падение пода или узла:**  
    Контроллеры (ReplicaSet/Deployment) автоматически создают новый под взамен упавшего для сохранения нужного числа реплик, а kubelet перезапускает контейнеры внутри пода.

22. **Что такое rolling update и какие параметры за него отвечают:**  
    Обновление без простоя путем плавной замены старых подов новыми. Параметры в Deployment: `maxSurge` (сколько можно создать сверх нормы) и `maxUnavailable` (сколько может быть недоступно).

23. **Как запустить обновление приложения и следить за прогрессом:**  
    Запуск: `kubectl set image deployment/<name> <container>=<image>` или `kubectl apply`. Отслеживание: `kubectl rollout status deployment/<name>`.
